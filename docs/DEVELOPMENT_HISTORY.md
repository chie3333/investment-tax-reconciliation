# 개발 과정과 설계 의사결정 — 초기 버전과 후속 구현

> 프로젝트: **Investment Tax Reconciliation (투자주식 회계·세무조정 검토 시스템)**  
> 범위: 초기 웹앱 → KRX 연동 → 계산 검증·정책 개선 → 세무원가 통합·결산월 개선 → 자동 검증·SQLite → **v4 FVOCI 회계·세무 로직 수정**  
> 작성일: 2026-10-26  

1~5절은 초기~v4 당시의 판단과 미완료 기록이다. 당시 상태를 보존하며 체크박스를 소급 변경하지 않는다. 후속 완료 내역은 6절, 현재 기준은 [구현 완료 현황](IMPLEMENTATION_STATUS.md)을 참고한다.

## 1. 왜 이 프로그램을 만들었나

출발점은 **국내 상장주식에 대한 회계처리와 법인세 세무조정을 한 흐름에서 계산·검토하는 웹앱**이다. 매수·매도·배당·기말평가 같은 거래에서 회계상 장부금액과 세법상 장부금액이 달라지는 이유를 추적하고, 특히 **FVOCI/FVTPL 분류의 차이**와 **세무조정·유보 변동**을 설명 가능하게 만드는 것이 목적이었다.

개발하면서 목표는 더욱 분명해졌다.

- 단순한 손익 계산기보다 **회계원장과 세무원가의 차이를 대사하는 검토 도구**를 지향한다.
- 계산 결과만 제시하지 않고 **적용 정책, 거래 원천, 계산 과정과 오류를 확인**할 수 있어야 한다.
- 동일 종목을 회계상 FVOCI/FVTPL로 나누더라도 **세무원가 계산의 단위는 별도 검토**해야 한다.
- **OCI에 인식된 회계 금액과 당기손익에 인식된 금액을 구분**하여 세무조정을 생성해야 한다.
- 자동 계산을 곧바로 세무신고의 법적 결론으로 간주하지 않는다.

## 2. 변화의 흐름: 요청 → 판단 → 반영 → 남은 문제

### 단계 0. 첫 웹앱: 투자주식 거래·평가·세무조정의 한 화면 통합

**원래 만들고자 한 것**

종목과 보유자산을 등록하고 매수·매도·배당 및 공정가치 평가를 입력하면, FVOCI/FVTPL 회계 처리와 세무상 원가·세무조정 결과를 계산·표시하는 브라우저 웹앱.

**초기 구현 방향**

- `index.html` 중심의 단일 페이지 웹앱.
- 종목 마스터, 회계분류별 보유자산, 거래 및 평가 기록, 계산 결과와 CSV 내보내기.
- 초기 업무 데이터는 브라우저 `localStorage`에 저장.
- 회계원가와 세무원가의 차이를 보이는 기능은 있었으나, 유보의 발생·환입과 법정 신고서상 소득처분을 독립적으로 검증하는 장부는 미완성이었다.

**첫 번째 구조적 한계**: 브라우저 내부 계산과 저장을 중심으로 만들어져 **서버 측 검증, 변경 이력, 외부 기준가격 확보**가 별도 과제였다.

### 단계 1. KRX 시세 조회 추가: 자동 가격 확보와 실제 거래가격 구분

**요구·결정**

거래일·평가일의 상장주식 종가를 자동으로 조회해 수기 입력 부담을 줄이되, **시세가 실제 체결가를 의미하지는 않도록** 했다.

**반영** 

- Python `server.py`가 KRX Open API 호출을 중계하도록 구성.
- 거래 화면의 취득일 종가 조회, 평가 화면의 평가일 종가 조회 및 보유종목 일괄 조회.
- 휴장일은 이전 영업일 가격을 찾는 선택적 조회를 두고, **원래 요청한 평가일과 실제 가격 기준일을 구별**하도록 설계.
- API 키는 브라우저가 아니라 환경변수에서 읽도록 함.

**남은 문제**

- KRX API 키·이용 승인 및 실서비스 응답을 사용한 통합 테스트 미완료.
- 시세 자동 조회가 거래 증빙이나 실제 취득단가의 검증을 대신할 수는 없음.
- 이 단계의 서버는 가격 프록시였으며, 거래 데이터는 여전히 `localStorage`에 저장되었다.

### 단계 2. ‘계산값이 맞는가’부터 확인: 독립 검산 엔진과 테스트

**요구·판단**

화면이 동작하는 것보다 중요한 것은 **계산이 맞는지 재현 가능한 사례로 확인하는 것**이었다. 동일한 JavaScript 계산 함수만 다시 호출하면 로직 자체의 오류를 잡기 어렵다는 문제의식이 생겼다.

**반영** 

- 별도 Python `Decimal` 기반 `validation/engine.py` 참조 계산기 추가.
- FVTPL의 매수·매도·평가·배당, 이동평균법/연도별 총평균법 시뮬레이션.
- 당기손익, 회계상 장부금액, 세무상 장부금액 및 그 차이에 대한 테스트 작성.
- 초기 5개 자동 테스트 마련.

**남은 문제**

- 이 엔진은 **독립 검산용**이었고, 당시 웹앱 계산 결과를 매번 자동으로 검산하지는 않았다.
- 초기 참조 엔진은 FVTPL 중심이었으며 FVOCI, 원단위 반올림, 거래비용, 법인세 특례 등은 범위 밖이었다.
- ‘장부금액 차이 = 신고서상 유보’로 단정할 수 없으므로, 이후 세무조정의 방향과 소득처분을 구분할 필요가 있었다.

### 단계 3. 세무원가 정책 재설계: 종목별 선택 → 법인·사업연도별 관리

**문제 제기**

초기에는 종목별로 총평균법 또는 이동평균법을 선택할 수 있었지만, 실제 세무원가 계산 방법은 회사의 신고 및 적용 사업연도와 연결되어야 했다. 사용자는 **사업연도별 적용 정책 및 신고·변경 이력**을 남길 것을 요구했다.

**반영 방향** 

- 법인 단위 기본 원가계산 방법과 사업연도별 적용 정책을 구별.
- 정책 변경이 과거 연도 계산까지 임의로 바꾸지 않도록 적용연도와 신고 상태를 기록.
- 법령상 신고 여부·변경 효력·미신고 기본값 등은 단순 UI 설정과 구분해야 한다는 검토 항목을 추가.

**핵심 변화**: ‘종목마다 계산법 선택’이라는 편의 기능보다 **회사에 적용되는 세무정책의 연속성**을 우선하게 됐다.

**남은 문제**: 정책을 입력했다고 해서 법령상 유효하게 신고·변경된 것까지 자동 확인하는 것은 아니었다.

### 단계 4. 동일 종목의 세무원가 풀 통합: FVOCI/FVTPL 구분과 별개로 계산

**문제 제기**

> “회계상 FVOCI와 FVTPL로 나뉘어 있어도 같은 종목의 세무원가를 각각 따로 계산하는 게 맞나?”

동일 종목·동일 권리 주식을 회계상 서로 다른 분류로 관리한다는 이유만으로 세무상 처분원가까지 분리 계산하면 **잘못된 세무원가와 조정 금액**을 만들 수 있다는 점을 발견했다.

**반영 방향** 

- 세무원가 계산을 `stock_code` 기준의 **통합 원가 풀**로 전환.
- 회계장부와 거래 이력은 FVOCI/FVTPL 자산별로 유지.
- 기말 보유수량 등을 이용해 통합 세무원가를 회계분류별로 다시 배분하고, 합계가 원가 풀 잔액과 일치하는지 대사.

**핵심 설계**

```text
회계장부:  [동일 종목 / FVOCI]   [동일 종목 / FVTPL]
                      ↘         ↙
세무원가:           [종목별 통합 풀]
                      ↙         ↘
보고·대사: [FVOCI 배분세무원가] [FVTPL 배분세무원가]
```

**남은 문제**

- 당시 기말 분류별 원가 배분과 **개별 거래별 유보 발생·환입 계산**이 완전히 연결되지는 않았다.
- 일부 거래 단계에서는 분류별 계산과 종목 전체 통합 풀 결과가 달라질 가능성이 남아 있었다.
- 부분 처분·전량 처분·원단위 잔여액 배분에 대한 독립 대사가 필요했다.

### 단계 5. 비12월 결산과 FVOCI 조정 분리

**문제 제기**

12월 결산만 전제로 계산하면 3월 등 다른 월에 결산하는 법인의 거래 귀속 연도가 어긋날 수 있었다. 동시에 FVOCI 평가·처분 금액을 단순 당기손익 조정으로 합산하고 있는 문제 발견

**반영** 

- `fiscalEndMonth`와 `fiscalYear(date)` 등을 도입해 비12월 결산의 사업연도 경계를 구분.
- 종목 통합 세무원가의 기말 분류별 배분·대사 보강.
- FVOCI 거래를 일반 당기손익 조정과 구분하는 임시 `ociTaxBridge` 지표 도입.
- 3월 결산, 분류별 배분, FVOCI 관련 계산에 대한 JavaScript 테스트 추가.

**중요한 한계**

`ociTaxBridge`는 OCI와 세법상 손익을 나란히 보여주는 **검토용 연결 금액**일 뿐, ‘익금산입/손금산입 × 유보/기타’ 등 법정 세무조정 명세의 완성된 대체물이 아니었다. 따라서 거래별 유보원장과 연도별 명세의 연결은 후속 과제로 남았다.

### 단계 6. 2단계 자동 검증 기획과 데이터 저장 전환

**오류 탐지 추가**

1. 보유수량 및 거래 오류
2. 기말평가 누락·기준가격 문제
3. 회계상·세무상 장부금액 대사
4. 유보 발생·환입과 전기 이월
5. 세무원가 계산방법·신고 정책

**방향 변경**

검증 결과와 수정·승인 이력을 보존하려면 `localStorage`만으로는 부족했다. 이에 **SQLite 저장, 변경 전후 감사 로그, 검증 실행 이력**을 도입했다.

**반영** 

- 거래·평가·정책 상태를 로컬 SQLite에 저장하는 서버 API 도입.
- 변경 전·후 이력을 남기는 감사 로그와 버전 충돌 탐지.
- 수량·중복거래·평가 누락·시세 기준일·세무원가 배분 불일치 등의 규칙 기반 검증.
- 검증 대시보드의 오류·경고·검토 상태 및 검증 이력 관리.

**한계**

- 모든 검증이 완전한 독립 재계산을 수행하지는 않았다.
- 당시 전기 확정잔액과 당기 기초유보를 연결하는 독립적인 결산·유보원장 통제는 아직 미완성이었다.
- 단일 사용자 로컬 환경을 넘어서는 인증·권한 관리는 범위 밖이었다.

### 단계 7. v4: FVOCI의 ‘회계상 인식 위치’와 ‘세무조정’을 구분

**문제 제기**

기존 계산을 확인했을 때, FVOCI 처분의 회계상 당기손익을 0으로 놓고 `ociTaxBridge`에 차이를 표시하는 것만으로는 **세무조정과 유보 환입이 제대로 연결되지 않았다**. FVOCI 지분상품은 누적 OCI를 처분 시 당기손익으로 재분류하지 않으므로, 평가·처분·자본 내 이동을 구별해야 했다.

**v4 반영** 

- FVOCI 평가손익과 처분 관련 금액을 **당기손익과 OCI**로 구분해 계산·표시.
- FVOCI 지분상품 처분 시 누적 OCI를 당기손익으로 재분류하지 않는 원칙을 반영.
- 누적 OCI의 처분 대상분 및 자본 내 대체 관련 금액을 별도 표시하도록 개선.
- 세법상 처분손익과 회계상 손익의 차이를 **세무조정 후보**로 분리.
- 법적 소득처분(`유보`, `△유보`, `기타`)을 계산 차이만으로 자동 확정하지 않고 **검토 필요** 상태로 처리.
- FVOCI 거래가 있는 사업연도에 추가 검토 경고를 표시하도록 검증 규칙 보완.

**중요: v4에서 ‘완성’한 것이 아닌 것**

- `기타`와 `유보`가 함께 필요한 **복수 조정 행**을 모든 거래에 대해 법령 근거까지 자동 확정하는 기능.
- FVOCI 부분 처분의 유보 발생·환입액을 통합 세무원가, 잔여 회계장부, 전기 이월과 **독립적으로 완전 대사**하는 기능.
- 승인된 세무조정만 유보원장에 전기하고, 결산 확정·취소·정정하는 통제. 이는 **v5~v6 이후 작업**에 해당한다.

## 3. 설계에서 가장 크게 바뀐 생각

| 주제 | 초기 접근 | v4까지의 개선 방향 |
|---|---|---|
| 계산 중심 | 거래 입력 후 금액 산출 | 입력 → 계산 → 독립 검증 → 차이 추적 |
| 원가 계산 정책 | 종목별 임의 선택 | 회사·사업연도 정책과 신고 이력 |
| 세무원가 단위 | FVOCI/FVTPL 분류별 계산 가능 | 동일 종목 통합 세무원가 + 분류별 배분 |
| 사업연도 | 사실상 12월 결산 중심 | 비12월 결산 경계 지원 |
| FVOCI 처분 | 간단한 OCI 차이 표시 | PL·OCI·누적 OCI 및 자본 내 이동 후보 분리 |
| 세무조정 | 손익 차액을 한 값으로 제시 | 조정 후보와 법적 소득처분을 구별 |
| 데이터 | 브라우저 `localStorage` | SQLite, 감사 로그, 검증 실행 이력 |
